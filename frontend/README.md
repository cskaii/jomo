# JOMO frontend

A responsive Next.js, React, TypeScript and Tailwind prototype based on `../blueprint.md`, documented in `../change.md`.

## Run locally

For the local prototype on Windows, start the backend from the repository root:

```powershell
.\scripts\start-prototype-backend.ps1
```

This uses the ignored `jomo_prototype.db` SQLite file and development identities, without changing `backend/.env` or touching shared Supabase data. The script restores process environment settings when it exits. Keep its terminal open. Do not use development identities with a shared/deployed database.

In a second terminal, open `frontend` and run `npm run dev`. If npm is unavailable but Node is installed, run `node .\node_modules\next\dist\bin\next dev --webpack` (or use the absolute path to your Node executable). Visit **http://localhost:3000**, click **Create development session**, then **Garden**. Both servers must remain running. A missing backend now produces an actionable connection message instead of an unexplained Network Error.


Requires Node.js 20.9 or newer and the existing FastAPI server.

```powershell
cd frontend
npm ci
Copy-Item .env.example .env.local
npm run dev
```

Open [JOMO](http://localhost:3000). Choose **Create development session** to initialize a local profile and personal garden. Browser requests default to `/api/v1` on the frontend, which proxies to the server-only `BACKEND_API_URL` (default `http://127.0.0.1:8000`). Keep `NEXT_PUBLIC_API_BASE_URL=/api/v1` for local/network access; override it only for an intentional separate API deployment. Restart Next.js after changing these settings. Never put privileged keys in this file.

Start the existing backend in a separate terminal from the repository root, after installing its requirements in your Python environment:

```powershell
$env:PYTHONPATH = (Get-Location).Path
python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

Use a disposable local database for demonstrations. Real accounts, signed photo storage and secure reward validation remain backend integration work. This frontend does not claim native app blocking or device-wide monitoring.

## Checks

```powershell
npm run typecheck
npm run lint
npm test
npm run build
npm start
```

Development/build scripts explicitly use Webpack with the official Tailwind PostCSS integration. The original Turbopack CSS loader failed to start its compiler subprocess on the verification machine. The monorepo root is configured so imports from `../shared` resolve.

## Structure

- `src/`, `public/`, `tests/`: application code, static assets and tests; keep these in version control.
- `node_modules/`: installed dependencies; generated by `npm ci`, ignored by Git.
- `.next/`: generated development/production output; recreated by the Next.js commands, ignored by Git.
- `package.json`, `package-lock.json`: dependency definitions and reproducible npm installs; keep both.
- `.pnpm-store/`: optional package download cache; not required to run the app and removed from this checkout. Use the npm commands above for this project. The ignore rule remains to prevent accidental commits if a cache is created again.

Application modules:

- `src/app`: thin route wrappers and shared layouts.
- `src/features/prototype`: feature screens, request state and accessible feedback.
- `src/lib/offline.ts`, `src/services/offline.ts`: caller-only completed-participation summaries for Insights and the personal garden; planned duration never counts as completed time.
- `public/images/woodland.svg`, `src/features/prototype/GardenScene.tsx`: original decorative woodland and inventory-driven garden illustrations.
- `src/services/apiClient.ts`: HTTP transport, development token and session/error handling.
- `src/services/prototype.ts`: Zod response boundaries and formatting utilities, compatible with `src/types` contracts.
- `src/services/gardens.ts`, `src/lib/gardenNavigation.ts`: accessible garden directory and URL-based garden selection.
- `src/features/prototype/GardenCarousel.tsx`, `GardenNavigation.tsx`: group previews and the right-side garden switcher.
- `src/proxy.ts`: request IDs; backend authorization remains required.
- `tests/contracts.test.cjs`: API boundary and UTC regression tests; no database writes.
- `tests/offline.test.cjs`: offline-minute, caller and date-boundary regression checks; no database writes.
- `tests/garden-navigation.test.cjs`: directory, personal-garden and group-link selection checks; no database writes.

## Supported prototype flows

The current visual design follows the supplied cream-and-olive references: serif headings, horizontal pill navigation, a woodland Today page, illustrated gardens and friend cards. Navigation has Insights, Garden and Friends. Activities are embedded directly below the garden previews; the old `/activities` listing redirects to `/garden?activities=1#garden-activities`, while creation/detail/focus routes remain available and activate Garden. Group tools live inside Garden; old `/squads` links redirect to `/garden?groups=1#garden-groups`. The category/duration popup creates a real activity plan and opens its detail screen. Its date is today, since the existing API does not support verified retrospective logging.

Garden (`/garden`) opens a carousel of the caller's personal and accessible shared gardens, with Personal/Shared badges. Use the arrows, keyboard or horizontal swipe to browse; click a preview to open that garden. The top-right hamburger opens a drawer from the right with all accessible group gardens and the personal garden. The selected garden is stored in `/garden?garden=…`, so refresh and browser navigation retain the selection. Existing `/garden?group=…` links still work; `/garden?view=personal` explicitly opens the personal garden. Accounts without groups see their personal garden. The collapsed **Grow with a group** section offers optional group creation, membership management and invitation-code joining. Personal garden links open a full-page plant illustration with visible offline time, points, growth level and rhythm statistics. The top-right button is removed. Back returns to the garden list; the inline Collection & shop link opens the existing management view at `?garden=…&manage=1`. The plant illustrates the server growth level independently of purchased inventory. Shared gardens keep their detail view.

Offline time comes from the current user's completed participation and returned eligible minutes. The dashboard's fixed 60-minute offline intention is a gentle visual benchmark, distinct from the saved screen-time goal and unrelated to rewards. Garden objects/points come from real inventory and balances. Email friend lookup, nudges, friend-garden visits and weekly competitions are not simulated; the supported friend-request form uses a profile ID, available on Settings.

Insights includes explicit sample import, manual usage, source labels, trends, categories, goals and optional coaching. Friends supports private circles, invite codes, membership/history and shared-garden links. Activities supports personal/group plans, participation, voluntary focus timers, one-shot location consent and proof status. Garden includes switching, inventory, purchase confirmation, placement and ledger history. Privacy Guardian submits text only on request and clears stale results when text changes. Settings saves profile, goals and privacy preferences.

Registration/reset screens explain that real accounts are not connected. Photo submission stops on the existing mock storage URL rather than inventing successful uploads. Rewards are displayed only from server participation/ledger responses. See `../change.md` for the full rationale and backend limitations.
